# Контекст проекта: Высокопроизводительная визуализация графа

## Цель проекта

Создать высокопроизводительную систему визуализации графа на React-Konva с поддержкой:
- Тысяч нод (Node) и связей (Link)
- Плавного перетаскивания нод и камеры
- Виртуализации - рендерить только видимые элементы

Система оптимизирована для сценария: тысячи нод, частые обновления положения карты (60 раз в секунду при drag), редкие обновления данных, плавная анимация.

---

## Архитектурные решения

### 1. Подписочная система вместо useState

**Проблема:**
- Компонент с провайдером не должен обновляться при изменении ноды
- Нод могут быть сотни и тысячи
- Ноды отдают событие onDrag с троттлом, но тем не менее очень быстрые события onNodeChange (60 раз в секунду)
- На каждую ноду подписано всего лишь 1-5 других объектов (называются Link), поэтому обновлять всё было бы безумием

**Решение:**
- Каждый LinkView подписывается на изменения конкретных нод (source & target)
- Каждый NodeView подписывается на свою grid-ячейку для отслеживания видимости
- Нет массовых ререндеров всего графа

**Результат:** O(1) обновление + уведомление только подписчиков конкретной ноды

### 2. Grid-виртуализация

**Проблема:**
- Проверять каждую ноду на видимость при перемещении области видимости - O(n)
- Для тысяч нод это становится узким местом

**Решение:**
- Делим канвас на grid ячейки (по умолчанию 100x100px, настраивается через `gridCellSize`)
- Ноды подписываются на свою grid-ячейку, ячейка уведомляет их о видимости
- При изменении viewport проверяем только ячейки, попадающие в видимую область

**Сложность:** O(количество_ячеек_в_viewport) вместо O(количество_нод)

**Пример:** Для viewport 1920x1080 и grid=100px: ~220 операций каждые 50ms

### 3. Мутация состояния в подписках

**Проблема:**
- Создание новых объектов для тысячи нод каждые 16ms тормозит

**Решение:**
- Мутируем флаг `isVisible` напрямую в объекте ноды через подписки
- Остальные данные остаются иммутабельными

**Важно:** Мутируем только `isVisible`, остальные данные иммутабельные

### 4. Пересоздание контекста при изменении nodes

**Проблема:**
- Массив нод меняется редко
- Если создать nodesRef и использовать ссылку в ctx - придётся потом чистить, обновлять данные

**Решение:**
- В зависимостях `const ctx = useMemo()` находится массив `nodes`
- На каждое изменение массива нод сносим всё и считаем заново
- Гарантирует актуальность данных и чистоту подписок

## Структура данных

### Ноды и связи

Ноды и линки - это части контента для отображения на канвасе.

**Типы:**
```typescript
type Node = {
  id: string
  name: string
  description?: string
  x: number
  y: number
}

type Link = {
  id: string
  source: string  // id ноды-источника
  target: string  // id ноды-цели
}
```

**Моковые данные (пример):**
```typescript
export const dataMock: { nodes: Node[]; links: Link[] } = {
  nodes: [
    { x: 0, y: 0, id: '1', name: 'first' },
    { x: -80, y: -160, id: '2', name: 'second' },
    { x: 20, y: 118, id: '3', name: 'long named node' },
    // ... больше нод
  ],
  links: [
    { id: '1', source: '1', target: '2' },
    { id: '2', source: '1', target: '3' },
    // ... больше связей
  ],
}
```

Линки ведут от одной ноды к другой. В реальности нод и линков будет гораздо больше.

### Zoom и камера

У родительского канваса есть обработчики `onDragMove`, `onDragEnd`, оба они сетят положение камеры над картой.

```typescript
const [zoom, setZoom] = useState({ x: 0, y: 0, k: 1 })
const [size, setSize] = useState({ width: 100, height: 100 })
```

Где:
- `x, y` - смещение камеры
- `k` - масштаб (приближение)
- `size` - размер viewport

## Ключевые компоненты

### CanvasContextProvider

Провайдер содержит всю логику подписок и grid-системы.

**Структуры данных:**
- `nodeIdToNodeRecord: Record<string, Node>` - все ноды по id
- `nodeIdToSubscriptionsRecord: Record<string, NodeSubscribeCb[]>` - подписки на изменения нод
- `gridCellToSubscriptionsRecord: Record<string, CellSubscribeCb[]>` - подписки на изменения видимости ячеек
- `gridCellToVisibilityRecord: Record<string, boolean>` - текущее состояние видимости ячеек

**API:**
- `subscribeToNode(nodeId, subscriberCb, shouldCallInstantly?)` - подписка на изменения ноды
- `subscribeToGridCell(cellKey, subscriberCb, shouldCallInstantly?)` - подписка на изменения видимости ячейки
- `onNodeChange(node)` - обновление ноды (вызывается при drag)
- `onZoomChange({ x1, x2, y1, y2 })` - обновление видимости (вызывается при скролле/зуме)
- `getGridCellByCoordinates(x, y)` - получение ключа grid-ячейки по координатам

**Инициализация:**
- При создании контекста все ноды добавляются в соответствующие grid-ячейки
- Для каждой ноды и ячейки создаются пустые массивы подписок
- Если ячейка не инициализирована, значит в ней нет нод, и оповещать некого

### NodeView компонент

Компонент отображения ноды на канвасе.

**Логика:**
- Подписывается на изменения своей ноды (координаты) через `useSubscriptionToNode`
- Подписывается на свою grid-ячейку (видимость) через `useSubscriptionToCellVisibility`
- При изменении координат ноды автоматически пересчитывает grid-ячейку
- Рендерит себя только если `isVisible === true`

**Обработка drag:**
- При перетаскивании вызывает `onNodeChange` с троттлом (70ms)
- Обновляет координаты ноды в контексте

### LinkView компонент

Компонент отображения связи между нодами.

**Логика:**
- Подписывается на две ноды: `source` и `target` через `useSubscriptionToNode`
- Перерисовывает линию при изменении любой из нод
- Использует координаты нод для отрисовки линии

## Производительность

### Метрики

- **onZoomChange:** ~220 операций каждые 50ms (для 1920x1080, grid=100)
- **onNodeChange:** O(1) + обновление подписчиков конкретной ноды
- **Подписки:** Каждая нода имеет 1-5 подписчиков (обычно это линки)

### Оптимизации

- Троттлинг событий drag (70ms для нод, 50ms для zoom)
- Виртуализация через grid-систему
- Минимальные ререндеры через подписочную систему
- Использование `useMemo` для стабильности контекста
- Правильные зависимости в хуках для избежания лишних подписок

---

## Важные моменты реализации

1. **Гарантировать существование структур подписок при инициализации**
   - Все ноды должны быть добавлены в grid при создании контекста
   - Для каждой ноды и ячейки должны быть созданы массивы подписок

2. **Аккуратная очистка при удалении нод из grid ячеек**
   - При изменении массива `nodes` контекст пересоздаётся полностью
   - Старые подписки автоматически очищаются через cleanup функции в useEffect

3. **Оптимизировать React рендеры**
   - Использовать `memo` для компонентов где необходимо
   - Правильные зависимости в хуках
   - Избегать лишних ререндеров через подписочную систему

4. **Валидация данных не требуется**
   - Вызываю события и подписываюсь только внутри проекта
   - Это не "внешнее" API, никто не передаст неправильный вызов

## Технические детали

### Grid-система

- Размер ячейки по умолчанию: 100px (настраивается через `gridCellSize`)
- Формат ключа ячейки: `"${gridX} ${gridY}"` (например, `"5 -3"`)
- Вычисление ячейки: `Math.floor(x / gridCellSize)` для каждой оси

### Подписки

- Подписки хранятся в массивах для каждой ноды/ячейки
- При отписке используется `splice` для удаления из массива
- Callback всегда вызывается с актуальными данными через ref pattern

### Обработка viewport

- `onZoomChange` получает координаты видимой области: `{ x1, x2, y1, y2 }`
- Вычисляются grid-координаты начала и конца видимой области
- Проходим по всем ячейкам в этом диапазоне и помечаем их как видимые
- Сравниваем с предыдущим состоянием и уведомляем подписчиков только при изменении
